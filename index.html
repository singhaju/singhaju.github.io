FEDAC: zero-trust access checks that stay fast

Why it matters

Organisations increasingly share cloud services across teams and with partners. Once signed in, users often receive the same broad access everywhere, whether the resource is low-risk or highly sensitive. Stronger checks typically add latency to every request, and controls that are too slow tend to be bypassed or disabled.

Core idea

Verify each caller once, at the assurance level each service requires, then issue a short-lived, narrowly scoped token. Services validate the token locally instead of calling a central server on every request.

What makes it new

  • 01
    Verify once, validate locally

    A central hub authenticates the caller, evaluates policy and issues a signed, short-lived token bound to one service. The service validates it locally, with no extra network round trip.

  • 02
    Assurance matched to risk

    Four authentication levels, from single sign-on up to a zero-knowledge proof. Low-risk services require a basic level and stay fast; sensitive services require a stronger one.

  • 03
    Privacy-preserving access

    For the most sensitive services, users prove they hold the required attributes without disclosing them (a zero-knowledge proof). Each service sees a different pseudonym and only the attributes it needs, so activity cannot be linked across services.

  • 04
    Continuous re-evaluation

    Before a token expires, it is renewed, re-issued under the current policy, or the user is asked to re-authenticate. When a policy changes or a risk signal appears, the affected tokens are revoked immediately.

  • 05
    Tamper-evident policy

    The policy set is anchored on a blockchain as a Merkle root, so any unauthorised change is detectable. The root is checked when a token is issued, not on every request, so it adds no per-request latency.

Who benefits

Banks, hospitals and public agencies that share services across clusters or with partners. Staff get fast access to routine services and strong verification on sensitive ones, while disclosing as little personal data as possible.

Results

In experiments on AWS, a service validates a token in 1.4 ms (median), at about 7,100 requests per second, benchmarked against three published designs. Under review at IEEE TDSC. Limitations: tested in a single AWS region, and the prototype signs attributes but does not yet encrypt them.

  • 1.4 msmedian authorization check
  • ~7,100requests/s on AWS EKS
  • Paper under review

Lessons learned

Separate the checks that must run on every request from those that can run once. Strong assurance and low latency can coexist when the expensive verification is done once and its result travels as a short-lived, narrowly scoped token.

My part

What I did

I built the implementation in Go and Rust: a hub that checks the caller once and issues a short-lived pass for one service, and a sidecar that checks that pass locally on every call. I also re-implemented published designs and compared them with FEDAC on AWS EKS.

  • Zero trust
  • Zero-knowledge proofs
  • Service mesh
  • Blockchain audit

Tech used Go, Rust, Groth16 zk-SNARKs, Envoy and Istio, IPFS, AWS EKS

U-HAP: one place for every Kubernetes access rule

Why it matters

Kubernetes runs a large share of today's cloud infrastructure. Its access controls are split across independent components, and its built-in roles can only grant access, never deny it. When rule types are combined, it is hard to tell which rule takes precedence, and a small misconfiguration can open an unintended gap.

Core idea

Represent every type of access rule in one unified graph. An authorisation request then becomes a single question: is there a path from the subject to the resource, and does it cross an explicit deny?

What makes it new

  • 01
    Four models, one graph

    Role-based (RBAC), attribute-based (ABAC), access control lists (ACL) and explicit deny rules are written in one policy language and compiled into the same graph. Each model keeps its own semantics; none is forced into another.

  • 02
    Deny always takes precedence

    Rules are evaluated in a fixed order, and no allow can override a deny, so combining models cannot create an unintended gap. Kubernetes' built-in RBAC cannot express a deny at all.

  • 03
    Precompiled for speed

    Policies are compiled into lookup tables in advance. A role check becomes a single bitwise AND, and a condition shared by many rules is evaluated only once.

  • 04
    Evaluate only applicable rules

    Each request skips the rules that cannot match it. New users require no rebuild, because their attributes arrive with each request.

U-HAP on Kubernetes: the API server sends each authorization request to the U-HAP webhook, which answers from a decision cache or a gate-aware index evaluator. An admin's policies go through a DSL loader that validates them, a graph builder that compiles them, and an in-memory graph registry.

Who benefits

Platform and security teams: a single place to write and review every type of access rule, deterministic decisions, and a clear precedence order that is easy to justify to an auditor.

Results

It produced the same decisions as Open Policy Agent (OPA) on the same test requests, and reached its first decision after a policy update about 2.7× faster than OPA at 2,000 policies. It received the Best Paper Award at IEEE JCSSE 2026.

  • Same decisions as OPA

Lessons learned

Make conflict resolution explicit and put the safe outcome first. "Deny, then allow, then deny by default" is easy to explain to an auditor and straightforward to test.

My part

What I did

With three co-authors, I co-developed the authorization webhook and its policy model in Python, checked that its decisions match Open Policy Agent, and presented the paper at JCSSE 2026 in Bangkok.

TU Alert: campus incident reports in LINE

Why it matters

On a large campus, it is not always clear where to report a broken light or a safety hazard, and a report that reaches the wrong office remains unresolved. Students need a simple way to report, and the responsible staff need to see it promptly.

Core idea

Let students report campus incidents through a channel they already use, and route each report directly to the office responsible.

What makes it new

  • 01
    No app to install

    Students report from within LINE with a photo or video and a map pin. Staff manage cases from LINE on their phones or from a web portal.

  • 02
    Predictable routing

    Reports are routed to departments by explicit rules (category and campus zone), not by a predictive model. This is deliberate: a misrouted report costs a student more than a slightly slower manual review.

  • 03
    Secure by design

    Four roles, with each user's role and department always read from the database, never from the request. Staff sign in with a second factor and re-confirm before sensitive actions. Emergency kill switches, data retention and deletion controls, and security scans on every change.

  • 04
    Privacy by design

    Every access to a student's personal data is recorded in an audit log first, and the system stores a keyed hash instead of the student ID itself.

AI agents for third-party risk at Allianz Ayudhya

Why it matters

Before engaging a new supplier, a company must assess that supplier's security, and a large company also receives the same kind of questionnaires from its own customers. Much of this work is manual, and many steps depend on sound human judgement.

Core idea

AI prepares the first draft and guides the process, while people retain the judgement.

What makes it new

  • 01
    Both sides of third-party risk

    One agent supports the company as a supplier (responding to security questionnaires); the other supports it as a buyer (running the risk assessment for a new vendor).

  • 02
    Traceable answers

    Each drafted answer cites its supporting evidence, a rationale and a confidence score, so reviewers can accept the clear cases and focus on the uncertain ones. A person reviews every answer.

  • 03
    Gap analysis, not just answers

    A gap analysis shows where current controls fall short of the questionnaire's requirements and recommends how to close each gap.

  • 04
    Guidance, not automation

    The guidance agent walks business owners through each step, explains its purpose, validates their inputs and flags anything important that is missing.

Who benefits

Security reviewers, who verify a drafted answer instead of writing each one from scratch; and business owners, who run a vendor review only a few times a year and need clear guidance.

Results

Both agents were tested on real, anonymised cases and presented at the end of my internship (31 Jul 2026). The tools are internal, so no screens or figures are shown.

    ZKAudit: audit cloud logs without revealing who you are

    Why it matters

    Logs are the primary evidence after a security incident. An auditor must be confident that the logs are authentic and complete, without revealing their identity to the provider under audit.

    Core idea

    Let an auditor prove they are authorised to inspect cloud logs without revealing their identity, and guarantee that they see the authentic log, not a substituted copy.

    • The auditor proves they hold a valid, correctly scoped credential with a zero-knowledge proof, which shows the credential is genuine without disclosing it.
    • Each audit session is bound to one exact, committed version of the log, so the cloud provider cannot present a different history.
    • Proof verification is distributed across several servers and batched, so anonymous authentication does not become a bottleneck.
    • The log is stored as a Merkle tree, so any single record can be verified without reading the entire history.

    Where it could go Cloud logs shared among internal security teams, external auditors and investigators.

    • Merkle commitments

  • SubmittedResearch, 1st of 2 authors

    PQ-SCVA-MCK: post-quantum authorization across Kubernetes clusters

    Why it matters

    When several clusters or organisations share access, a single incorrect decision can grant far more privilege than intended. As quantum computing advances, today's signatures may not remain secure, so records that must be trusted for years need post-quantum protection.

    Core idea

    Do not simply trust the access system's decision: verify it, including that no deny rule was omitted.

    • Each decision carries evidence of every applicable rule, both allow and deny, so a deny cannot be silently hidden.
    • Only the evidence a decision requires is verified: an allow, an explicit deny, or a default deny.
    • A role from one cluster receives only the permissions the other cluster agreed to grant, so an "operator" cannot be silently escalated to "cluster-admin".
    • Post-quantum cryptography (ML-DSA signatures, ML-KEM key exchange) is larger and slower, so its cost is paid once per session rather than on every request, and a policy change revokes only the decisions it affects.

    Where it could go Organisations that run Kubernetes across multiple clusters or with partners, need verifiable access decisions and are preparing for post-quantum cryptography.

    SWARM-Fog: edge servers that share work and heal themselves

    Why it matters

    Factories and other industrial sites run many small computers close to the machines. When one fails or becomes overloaded, its workload must move quickly, and a central controller is a single point of failure.

    Core idea

    Apply swarm intelligence: fog clusters share what worked, as ant colonies do through pheromone trails, with no central controller.

    • A shared knowledge map of load, link quality and recovery readiness that decays and reinforces over time, like pheromone trails.
    • Overloaded clusters are relieved by peers that pull work, while running tasks continue uninterrupted.
    • Self-healing: state is replicated in advance, and a failed coordinator is replaced quickly.
    • Clusters adopt scheduling and recovery strategies proven elsewhere, but only when they observe a measurable gain.

    Where it could go Industrial IoT sites with recurring workloads, where one site's experience can benefit the others.
