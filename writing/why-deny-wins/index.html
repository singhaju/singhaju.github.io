Why a deny rule should always win

Kubernetes RBAC can grant access but never deny it. In U-HAP, our JCSSE 2026 paper, an explicit deny is checked first, so no allow rule can undo it.

  • Kubernetes
  • Access control
  • Research

Kubernetes RBAC rules only add permissions: there is no RBAC rule that says "never". Other rule types, such as ABAC and ACLs, live in separate modules, so no single place shows which rule wins when two rules disagree.

The problem with mixed rules

One request can match an RBAC role, an ABAC condition and an ACL entry at the same time. If the order between them is implicit, the answer can depend on how the rules happen to be set up. That is how a forgotten allow rule can quietly undo a block that someone meant to be permanent.

The order we chose

In U-HAP, our team put RBAC, ABAC, ACL and explicit deny rules into one model with a fixed order of checks:

  • Deny first: if any deny rule matches, the answer is no.
  • Then the allow rules: ACL, then RBAC, then ABAC.
  • Default no: if nothing allows the request, it is refused.

Because deny is checked first and nothing after it can change a "no", an allow rule can never undo an explicit deny. The paper calls this a monotone safety property: adding allow rules cannot open a door that a deny rule closed.

Doing the work ahead of time

A fixed order only helps if it is also fast. U-HAP compiles the policies ahead of time into small indexes for each resource and action, so at request time the webhook looks only at rules that can apply, and repeated requests are answered from a decision cache.

We checked that U-HAP gives the same decisions as Open Policy Agent on the same policies. After a policy update, it reaches a first decision about 2.7× faster than OPA at 2,000 policies.

What I took from it

Make the conflict rule explicit, and put the safe answer first. "Deny wins, then allow, then default no" is easy to explain to an auditor and easy to test.

U-HAP won the Best Paper Award at IEEE JCSSE 2026. I am the 2nd of 4 authors: I co-developed the webhook and its policy model, and I presented the paper. Paper on IEEE Xplore
