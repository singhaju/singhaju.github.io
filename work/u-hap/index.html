U-HAP: one place for every Kubernetes access rule

One model for RBAC, ABAC, ACL and deny rules, compiled ahead of time, with the same answer every time.

Why it matters

Kubernetes runs a large share of today's cloud infrastructure. Its access controls are split across independent components, and its built-in roles can only grant access, never deny it. When rule types are combined, it is hard to tell which rule takes precedence, and a small misconfiguration can open an unintended gap.

U-HAP policy graph: ABAC, RBAC, hierarchy, ACL and deny rules in one graph. Each subject reaches the resource through a gate node, and the action is allowed only when the gate's condition holds; a deny node blocks an action for every user.

The gap

Kubernetes splits authorisation across separate modules (RBAC, Node, webhook, ABAC) that do not know about each other, and RBAC can only grant access, never deny it. A rule that mixes models, such as "ops may delete pods in production only in office hours, unless the pod is critical", has to be stitched together, with no one place to see which rule wins. Rules get duplicated, and decisions depend on the order of checks.

What is new

Treat authorisation as a compiler problem. One graph model covers RBAC, ABAC, ACL and deny rules. Policies are compiled ahead of time into indexes per resource and action, so a request only looks at rules that can apply to it. Deny always wins and rules are checked in a fixed order, so the same request always gets the same answer.

What I built

As second author, I co-developed the Kubernetes authorisation webhook and its policy model in Python, and checked that its decisions match Open Policy Agent on the same test requests. I presented the paper at JCSSE 2026 in Bangkok.

Result

  • ~2.7× fasterto a first decision after a policy update, vs OPA at 2,000 policies, with identical decisions

Compared with Open Policy Agent on the same policies; the method and setup are in the published paper.

Where it helps

Platform and security teams get one place to write and review every kind of access rule, and the same answer every time.

Limits and next

Rules are scoped to one namespace today. Next: cluster-wide and cross-namespace rules, recompiling only what changed, and multi-cluster deployments.

Lessons learned

Make conflict resolution explicit and put the safe outcome first. "Deny, then allow, then deny by default" is easy to explain to an auditor and straightforward to test.
