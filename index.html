FEDAC

The ideaCheck the caller carefully once, then check a short-lived pass cheaply on every call

Code on GitHub
Read the full story

1.4 msmedian authorization latency on AWS EKS, about 7,100 requests per second (paper under review)

The gap
In federated Kubernetes (several clusters, several organisations), the built-in RBAC is static: a role stays the same whichever service is called and however risky the request is. Adding risk-based sign-in, private cross-domain identities and tamper-evident policies usually puts heavy cryptographic or on-chain work on every request. The published designs we studied did not combine all of these without slowing requests.
What is new
Split the expensive work from the per-request check. A hub verifies the caller once, choosing the sign-in strength per service by its sensitivity: single sign-on, a one-time code, a context risk check, then a zero-knowledge proof. It checks the policy, stored on IPFS, against a Merkle root held on a blockchain, then issues a short-lived token scoped to one service. A sidecar checks that token locally through Envoy in Istio, with no network call. If a policy is tampered with or a security event occurs, only tokens for the affected services are revoked.
What I built
As first author in a team of four (two fellow students and Prof. Fugkeaw), I worked on the research design and built the implementation in Go and Rust: the hub, the Envoy external-authorization sidecar, four sign-in tiers including a Groth16 zero-knowledge verifier, targeted revocation and blockchain anchoring. I also re-implemented published designs and compared them with FEDAC on AWS EKS.
Where it helps
Example: a compliance analyst at a financial firm opens an audit dashboard, a risk-model service and a trading service in one session. Each service asks for the sign-in strength it needs, each call is checked on the spot, and every policy change can be audited later.
Limits and next
The first sign-in is still the slow step, so FEDAC suits services that call each other again and again. It was tested in one AWS region on a test blockchain, and the prototype signs private attributes but does not encrypt them yet. Hardware-backed keys and federation across regions are next.

  3. 03Short-lived token for one service
  4. 04Sidecar checks each call locally

U-HAP

The ideaOne place to write every Kubernetes access rule, with the same answer every time

Read the paperCode on GitHub
Read the full story

~2.7× fasterpolicy updates reach a first decision vs OPA at 2,000 policies, with identical decisions

The gap
Kubernetes splits authorization across separate modules (RBAC, Node, webhook, ABAC) that do not know about each other, and RBAC can only grant access, never deny it. A rule that mixes models, such as "ops may delete pods in production only in office hours, unless the pod is critical", has to be stitched together, with no one place to see which rule wins. Rules get duplicated, and decisions depend on the order of checks.
What is new
Treat authorization as a compiler problem. One graph model covers RBAC, ABAC, ACL and deny rules. Policies are compiled ahead of time into indexes per resource and action, so a request only looks at rules that can apply to it. Deny always wins, so every decision is deterministic.
What I built
As second author in a team of four, I co-developed the Kubernetes authorization webhook and its policy model in Python, and checked that its decisions match Open Policy Agent on the same test requests. I presented the paper at JCSSE 2026 in Bangkok.
Where it helps
Platform and security teams get one place to write and review every kind of access rule, and the same answer every time.
Limits and next
Rules are scoped to one namespace today. Next: cluster-wide and cross-namespace rules, recompiling only what changed, and multi-cluster deployments.

    MoCA: AI containment

    Keep a hijacked AI agent inside what its human allowed: an MCP gateway and resource-side checks

    In preparationFirst authorPrivate repository
    Read the full story
    The idea
    Authority is checked when an action is committed, not when it is planned. Permissions can only shrink as one agent delegates to another, revocation can be verified, and text from untrusted sources, such as a web page with a hidden instruction, cannot trigger actions beyond its limit.
