Zero trust without paying for it on every request

In FEDAC, a hub checks the caller carefully once and issues a short-lived pass, and a sidecar checks that pass on every call. The paper is under review.

  • Zero trust
  • Kubernetes
  • Research

Zero trust means no request is trusted by default: every call between services is checked, even inside the network. The hard part is the cost. Strong checks, such as a second sign-in step, a zero-knowledge proof or a lookup on a blockchain, are slow. If every request pays for them, the whole system slows down.

The setting

FEDAC is built for federated Kubernetes: several clusters, run by several organisations, whose services call each other. The built-in RBAC is static there. A role stays the same whichever service is called and however risky the request is.

Split the slow part from the fast part

  • Check once, carefully. A hub verifies the caller. The sign-in strength depends on how sensitive the service is: single sign-on, then a one-time code, then a check of the request's context and risk, then a zero-knowledge proof for the most sensitive services.
  • Check the policy too. Policies are stored on IPFS, and the hub checks them against a Merkle root held on a blockchain, so a changed policy is noticed.
  • Issue a short-lived pass for one service. The caller gets a token that works only for that service, and only for a short time.
  • Check the pass locally on every call. A sidecar next to each service checks the token through Envoy in Istio, with no network call.

If a policy is tampered with or a security event happens, FEDAC revokes only the tokens for the affected services, not every session.

What I built

I am the first author. I worked on the research design with the team and built the implementation in Go and Rust: the hub, the Envoy sidecar, four sign-in tiers including a Groth16 zero-knowledge verifier, targeted revocation and the blockchain anchoring. I also re-implemented three published designs (Heimdall, ZKP-CapBAC and Atalay) and compared them with FEDAC on AWS EKS.

We compared FEDAC with the three designs on AWS EKS. The numbers are in the paper, which is under review.

Limits

The first sign-in is still the slow step, so FEDAC suits services that call each other again and again. We tested it in one AWS region on a test blockchain, and the prototype signs private attributes but does not encrypt them yet.

What I took from it

Ask which checks must happen on every request and which can happen once. Strong checks and fast requests can live together if the slow work is done once and its result travels as a short-lived, narrow pass.

FEDAC is under review at IEEE TDSC. I am the first author, supervised by Prof. Somchart Fugkeaw. More on the FEDAC case page.
